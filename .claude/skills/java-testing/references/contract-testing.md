# 契约测试 vs WireMock 选型

Pact / Spring Cloud Contract 的 API 写法 AI 已熟。本文档只回答**何时引入 CDC**。

## 一句话区分

- **WireMock**：我自己写"假设上游怎么响应"。可能与真实上游漂移。
- **CDC（Pact / Spring Cloud Contract）**：消费者 + 生产者共享契约文件，CI 双向校验，任何一方破坏契约都立即挂。

## 决策树

```
要 mock 的上游是谁？
├─ 第三方（支付、AI、银行）         → WireMock + 监控真实接口契约快照
├─ 公司内部另一团队的服务
│   ├─ 能推动对方接入 CI            → CDC（优先 Pact，消费者驱动）
│   └─ 推不动                       → WireMock，但要记录契约漂移风险
└─ 同仓库 / 同服务                   → 不 mock，直接集成测试
```

## 工具选择

- **Pact**：消费者驱动 + 跨语言友好。**优先选这个**。
- **Spring Cloud Contract**：生产者驱动（生产者写契约→生成 stub），更像"发 SDK"。全栈 Spring 团队可选。

## 现状自检：要不要引入 CDC

命中 ≥ 2 项就该引入：

- [ ] 上游接口结构近半年改过 ≥ 3 次而你提前不知道
- [ ] "联调炸了" 是常见反馈，每次都是字段改名 / 类型变更
- [ ] 上下游不在同一团队，沟通有摩擦
- [ ] 消费者 ≥ 3 个，跨多团队 / 多语言

否则继续用 WireMock + 集成环境冒烟即可。

## CDC ≠ 全覆盖

只对**关键业务接口**（涉及钱、状态变更、不可逆操作）做 CDC，CRUD 接口 WireMock 即可。契约维护成本不容低估。

## 与项目内其他 mock 方案的关系

| 方案 | 解决什么 |
|------|---------|
| AOP Mock 切面 | QA 在测试环境复现上游故障（401 / 超时 / 限流） |
| WireMock | 开发跑集成测试时不依赖真实上游 |
| CDC | 上游悄悄改 schema 让我集成时炸 |

三者并存，不互斥。
